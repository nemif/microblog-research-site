## 2. T2 — Анализ конвейера «эксперимент → артефакт → страница»

| Способ | Где выполняются вычисления | Плюсы | Минусы |
|---|---|---|---|
| Ручная публикация PNG | Вне сборки | Простой и дешёвый в CI | Результат легко рассинхронизировать с данными |
| nbconvert / MyST-NB / Quarto | Во время сборки или отдельного рендера | Ноутбук и отчёт связаны | Долгие сборки, сложные зависимости, недетерминированные выводы |
| papermill | Запуск параметризованного ноутбука | Пакетные эксперименты | Стоимость, требования к окружению |
| Makefile / внешний скрипт → CSV/Markdown | Перед сборкой сайта | Контроль версий и кэша, простой CI | Нужно отдельно обслуживать генератор |

Выбор: вычисления по тяжёлому эксперименту выполнять отдельно, хранить сырые результаты, версии данных, хеши и метаданные, а в CI создавать только публикационные артефакты. Это снижает расход ресурсов CI и уменьшает различия между прогонами.

CI ограничен вычислительными ресурсами, временем выполнения, кэшем и отсутствием гарантированного GPU. Перед научной публикацией фиксируются: Git SHA, версии зависимостей и контейнеров, SHA-256 CSV, параметры эксперимента и метаданные запусков.

## 3. P3 — Воспроизводимый конвейер

Скрипт `scripts/generate_results.py` читает CSV, создаёт `docs/results.md` и `docs/assets/lcp.svg`. SHA-256 входных данных и кода определяет попадание в кэш.

**Выполнить демонстрацию:**

1. Запустить `python scripts/generate_results.py` — сохранить лог `CACHE MISS`.
2. Запустить снова — сохранить лог `CACHE HIT`.
3. В отдельной ветке изменить число в CSV тестовым образом, сделать commit/push; проверить обновление Markdown, графика и сайт-превью/Pages после слияния в main. Не выдавать демонстрационные изменения за реальные измерения.
4. Вернуть исходные данные и зафиксировать восстановление исходного графика.

**Снимки экрана, которые нужно приложить:** изменённый CSV, коммит, Actions, опубликованная страница, хеш данных.

## 6. Модель публикации и безопасность

В GitHub Pages используется официальный механизм `upload-pages-artifact` + `deploy-pages`. По сравнению с push в ветку `gh-pages` он не требует отдельного коммита сборки и использует `pages:write` с OIDC `id-token:write`. Helios требует отдельного SSH-ключа и проверенного `known_hosts`; ключ хранится в GitHub Secrets. Внешние CDN нужно проверять отдельно: тема Material может загружать внешние шрифты и вспомогательные ресурсы; без локализации этих ресурсов работу offline считать подтверждённой нельзя.
